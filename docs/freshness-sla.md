# Freshness SLA — the 90-day re-verification system

The reference for everything that enforces "this list stays current". One sentence to hold on to: **every verified entry must be re-confirmed against the provider's own docs within 90 days, and the worst entry drives every freshness signal in the project.**

This is the machinery behind the claims you see everywhere — the shields badge, the worklist, the re-verification batch, and the coloured `VERIFIED` column on the home page. For what "verified" *means* (and what it doesn't), see [methodology.md](methodology.md); for the weekly ritual that acts on this system, see [update-playbook.md](update-playbook.md); for the fields involved, see [comparison-dimensions.md](comparison-dimensions.md).

## 1. The policy

- **SLA:** a verified entry is re-confirmed against its own docs at most every **90 days**.
- **Due-soon warning:** once an entry is past **60 days** it is flagged as needing attention before it breaches the SLA (the boundary is exclusive: `freshnessStatus(60)` is still `fresh`, 61 is the first `due` day).
- **Never-verified** entries are treated as due — they need attention too.

The two numbers live in exactly one place, [`scripts/lib/rules.mjs`](../scripts/lib/rules.mjs), as `SLA_DAYS = 90` and `DUE_SOON_DAYS = 60`. Every consumer — badge, worklist, verified column, trust summary — imports or serialises them from there rather than re-declaring them, so the project can never show one signal green and another red for the same entry.

## 2. The three buckets

Age is measured in whole days from `last_verified` (`ageInDays` in `rules.mjs`); the age maps to exactly one bucket:

| Age | Bucket | Colour | Meaning |
|---|---|---|---|
| `null` / never verified | `due` | yellow | needs its first independent verification |
| ≤ 60 days | `fresh` | green | inside the SLA with room to spare |
| 61–90 days | `due` | yellow | due for re-verification soon |
| > 90 days | `stale` | red | breached the SLA |

The mapping is `freshnessStatus(age)` in `rules.mjs`. Its consumers — the repo-wide badge (§3), the worklist (§4) and, since the shared-rows refactor, the `VERIFIED` column in the explorer table (§6), with the trust line (§7) reading the same numbers — all draw from this one function (or its serialised copy), so they cannot disagree about an entry's state.

## 3. The badge (`site/badge-freshness.json`)

The shields.io freshness badge is generated by `scripts/build.mjs` via `freshnessBadge(providers, today)` in `rules.mjs`.

**It is graded on the oldest verified entry, not on the share of entries inside the SLA.** The share was unusable as a signal: because the list is re-verified in sweeps, a share-based badge could not leave brightgreen until roughly a third of the dataset had gone overdue — about four months of complete silence. It measured whether the project was still alive, not whether the data was fresh. The worst entry moves the day maintenance stops, and it is also the number a reader actually needs: the staleness of the row they are about to trust. (Full discussion in [methodology.md](methodology.md).)

| Oldest verified entry | Badge colour |
|---|---|
| ≤ 60 days | `brightgreen` |
| 61–90 days | `yellow` |
| > 90 days | `red` |
| nothing verified | `red` |

**One override:** if fewer than 70% of rows are verified at all, a brightgreen badge drops to yellow, however recent those verifications are. Coverage still counts.

**Date-relative by design.** The badge must move when time passes, not only when the data changes — a freshness badge that only moves when the data moves is not measuring freshness. So the badge is **not committed**: the build writes `site/badge-freshness.json` (gitignored) and every deploy, including the daily one, publishes it at `https://freellmapihub.com/badge-freshness.json`, which the README badge reads. It is outside both drift gates, it is never part of a pull request, and it ages at most a day. Nothing may assert that a badge built on one day equals one built on another.

## 4. The worklist (`npm run worklist`)

[`scripts/staleness.mjs`](../scripts/staleness.mjs) prints a Markdown re-verification checklist from the data. Report-only — it never edits anything and never fails. Sections:

- **🔴 Overdue** (`> 90` days) — every entry that breached the SLA, oldest first.
- **🟡 Due soon** (`61–90` days) — entries that will breach it next, oldest first.
- **⚠️ Never independently verified** — `verified: false` entries, with the first sentence of their `notes` as context.
- **📅 This week's batch** — the pacing target, sized as described below.
- **⛰️ Cliff watch** — only when relevant, described below.
- **📊 Freshness histogram** — for each of the next 16 weeks (Monday to Sunday, UTC), how many verified entries reach day 61 (`due`) and day 91 (past the SLA) if nobody re-checks them first. A week with more than 8 entries becoming due is marked ⛰️. The same table, anchored on the dataset date so the build stays deterministic, is on the [/coverage/](https://freellmapihub.com/coverage/#freshness) page. Code: [`scripts/lib/freshness-histogram.mjs`](../scripts/lib/freshness-histogram.mjs).

**Cliff watch.** A "cliff" is a cluster of entries that share one verification date and therefore cross the 90-day SLA together — the end-of-quarter hit that comes from sweeping the list. The script detects any date shared by ≥ 8 verified entries, and if that cluster crosses the SLA within 45 days it warns with the exact crossing date and how many days remain, so a few can be re-verified early each week to spread the load instead of taking the hit all at once.

**Batch sizing.** [`scripts/lib/pacing.mjs`](../scripts/lib/pacing.mjs) `weeklyPlan` sizes and picks the batch, the same way for the worklist and `npm run reverify`:

- **Size:** at least the approved pace of **6 a week** (owner decision, December 2026; one batch reviewed as one pull request), more when a simulation of weekly batches shows that 6 cannot keep every entry inside the 90-day SLA, and at most 11. If even 11 is not enough, the worklist says so.
- **Who qualifies:** entries that would cross the SLA before next week always go first. Otherwise an entry must be at least 28 days old, so a page checked last month is not checked again, **except while a coming week has more than 8 entries reaching day 61**: then every entry due no later than the last such week may be pulled forward from 7 days old. This is what spreads a same-day cohort, such as the 45 entries verified on 2026-11-19 and 2026-11-20, over the weeks before its due date instead of letting all of it expire in one week.
- **Order:** oldest verification first, ties by slug, so the batch never depends on the order of `providers.json`.

At 6 a week, a list of about 70 entries is re-checked every 11 to 12 weeks: inside the 90-day SLA, but past the 60-day line where the badge turns amber for some weeks in each cycle. Keeping the badge green all the time would need about 9 a week.

**Issue publication.** [`scripts/refresh-worklist.mjs`](../scripts/refresh-worklist.mjs) (`npm run worklist:refresh`) previews this exact renderer with one UTC clock and an immutable dataset link at the checked-out HEAD. Only explicit `--write` replaces [issue #4](https://github.com/pacocartones/free-llm-api-hub/issues/4)'s body; identical bodies skip the write. The entire body is generated, so each refresh resets checkboxes; discussion belongs in comments, and checked boxes are not evidence of completed provider verification. Title, state, labels, assignees and comments are preserved.

[`weekly-worklist.yml`](../.github/workflows/weekly-worklist.yml) publishes from trusted main Mondays at 09:17 UTC (10:17 Madrid winter / 11:17 summer), best effort, and allows manual dispatch on main. Forks and other refs cannot publish; overlapping runs are serialized. For delayed/disabled schedules, preview then explicitly write from a clean current-main checkout as described in [the playbook](update-playbook.md#recover-a-stale-issue-worklist). Closed/missing issues, malformed replies and write failures fail visibly without creating or reopening anything.

Every report says **Worklist refresh only; provider claims were not re-verified.** Publication never fetches provider sources or changes verification dates, evidence, the dataset or generated site/badge artifacts. A recent worklist date neither clears a verification backlog nor proves any provider fact.

## 5. The re-verification batch (`npm run reverify`)

[`scripts/reverify.mjs`](../scripts/reverify.mjs) picks the same batch as the weekly worklist. By default it only prints metadata. A human reviewer may opt into fetching untrusted provider prose into the operating system's temporary `free-llm-api-hub/reverify-human-only/` directory, outside the checkout:

```bash
npm run reverify                                  # safe worklist; no remote fetch
npm run reverify -- --batch 12                    # override the worklist size
npm run reverify -- --fetch-for-human-review      # human reviewer only
```

The script never edits `data/providers.json`. Provider pages and dossiers are untrusted and for human review only; do not provide them to a tool-capable agent. Transfer only the human-authored edit into a fresh worktree for repository-local regeneration and validation. Do not use a checkout containing either the current temporary dossier directory or legacy `.freebuff/reverify*` directories for the agent phase.

## 6. The `VERIFIED` column (SLA-aware)

Since the shared-rows refactor, the home-page table no longer shows every verified row with the same green check. The badge in the `VERIFIED` column is coloured by the same `freshnessStatus` buckets as the badge and worklist:

- **green** — fresh (≤ 60 days)
- **yellow** — due (61–90 days)
- **red** — stale (> 90 days)
- **yellow "unverified"** — never verified

Hovering shows `Verified Xd ago · YYYY-MM-DD`. The unverified case shows a yellow `unverified` badge with no date.

**Two renderers, one function.** The row markup lives in a single function, `explorerRowHtml` in [`scripts/lib/rows.mjs`](../scripts/lib/rows.mjs). `scripts/build.mjs` uses it for the server-rendered table (passing `data.generated` as the reference date, so the first paint is deterministic and the drift gate never trips on a calendar boundary), and serialises the same function to `site/shared-rows.js` (via `clientBundle()`), which the browser executes on every filter/sort repaint (passing `Date.now()`, so visitors see live freshness). Server and client cannot drift because it is literally the same function — the two-places rule from [architecture.md](architecture.md) applied to the table itself.

## 7. The trust summary line

The hero's trust line — `N/N verified against official docs · oldest entry 15d · 90-day re-verification SLA` — is computed client-side in `site/explorer.js` from the same rules: verified count, oldest age, and `SLA_DAYS` pulled from `shared-rules.js`. It is a read-out of §2 and §3, not a separate claim.

## 8. Invariants a change must not break

- **One set of buckets.** Any code that buckets an entry by age must call `freshnessStatus` from `rules.mjs` (or consume the serialised copy) — never re-declare the thresholds.
- **A verified entry needs its date and source.** `scripts/validate.mjs` rejects `verified: true` without `last_verified` and a real `docs_url`.
- **The dataset date is the release date.** `generated` (top of `data/providers.json`) is the day of the dataset release and moves only with `version` (`scripts/check-release-stamp.mjs`); a release must date it on or after the newest `last_verified`/`added`. No date of the dataset may be after today in UTC (`scripts/validate.mjs`). Every public date and every age the build computes use the newest date recorded in the data (`datasetAsOf`), so a verification made after the release still counts.
- **Nothing committed may be relative to the current date.** The freshness badge, the one output that moves with the clock, is not committed (`site/badge-freshness.json`, built on deploy); the NEW badge and freshness colours in `site/index.html` are computed from the newest date recorded in the data (`datasetAsOf`), so they are deterministic per dataset. Provider pages under `site/p/` are gitignored precisely so they may use the current date; everything else committed must be byte-stable for a given dataset.
- **Schedules publish metadata, never provider verification.** The weekly issue workflow (§4) recomputes ages and publishes the shared worklist; it performs no provider requests, dataset writes, evidence collection or badge regeneration. The local renderer remains available when schedules are delayed or disabled. Human review and dataset edits alone advance verification dates. The committed `badge-freshness.json` is recommitted on data/build passes (date-relative by design, §3). The `models_free` backfill (`npm run models`), probes and provider verification remain local and on-demand. Daily Pages deployment builds the site and refreshes GitHub stars without committing data; scheduled security scans are separate from provider maintenance. `verify.yml` remains a per-change integrity gate.

## Glossary

| Term | Definition | Where implemented |
|---|---|---|
| SLA | 90-day max age for a verification | `SLA_DAYS` in `rules.mjs` |
| Due soon | 60-day warning threshold | `DUE_SOON_DAYS` in `rules.mjs` |
| `fresh` / `due` / `stale` | the three age buckets | `freshnessStatus` in `rules.mjs` |
| Age | whole days since `last_verified` | `ageInDays` in `rules.mjs` |
| Badge | repo-wide shields badge, graded on the oldest entry | `freshnessBadge` in `rules.mjs` → `site/badge-freshness.json` (deployed, not committed) |
| Worklist | per-entry re-verification checklist | `scripts/staleness.mjs` |
| Batch | this week's oldest-N re-verification targets | `weeklyPlan` in `scripts/lib/pacing.mjs`, used by `staleness.mjs` and `reverify.mjs` |
| Histogram | entries reaching day 61 / day 91 per week | `scripts/lib/freshness-histogram.mjs`, in the worklist and on /coverage/ |
| Cliff | a date-cluster crossing the SLA together | cliff-watch section of `scripts/staleness.mjs` |
| Verified column | SLA-coloured check + age tooltip per row | `explorerRowHtml` in `scripts/lib/rows.mjs` → `site/shared-rows.js` |
