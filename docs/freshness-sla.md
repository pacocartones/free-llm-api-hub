# Freshness SLA — the 90-day re-verification system

The reference for everything that enforces "this list stays current". One sentence to hold on to: **every verified entry must be re-confirmed against the provider's own docs within 90 days, and the worst entry drives every freshness signal in the project.**

This is the machinery behind the claims you see everywhere — the shields badge, the worklist, the re-verification batch, and the coloured `VERIFIED` column on the home page. For what "verified" *means* (and what it doesn't), see [methodology.md](methodology.md); for the weekly ritual that acts on this system, see [update-playbook.md](update-playbook.md); for the fields involved, see [comparison-dimensions.md](comparison-dimensions.md).

## 1. The policy

- **SLA:** a verified entry is re-confirmed against its own docs at most every **90 days**.
- **Due-soon warning:** once an entry is past **60 days** it is flagged as needing attention before it breaches the SLA (the boundary is exclusive: `freshnessStatus(60)` is still `fresh`, 61 is the first `due` day).
- **Never-verified** entries are treated as due — they need attention too.

The two numbers live in exactly one place, [`scripts/lib/rules.mjs`](../scripts/lib/rules.mjs), as `SLA_DAYS = 90` and `DUE_SOON_DAYS = 60`. Every consumer — badge, worklist, verified column, trust summary — imports or serialises them from there rather than re-declaring them, so the project can never show one signal green and another red for the same entry.

## 2. The three buckets

Age is measured in whole days from `last_verified` (`ageInDays` in `rules.mjs`); the age maps to exactly one bucket:

| Age | Bucket | Colour | Meaning |
|---|---|---|---|
| `null` / never verified | `due` | yellow | needs its first independent verification |
| ≤ 60 days | `fresh` | green | inside the SLA with room to spare |
| 61–90 days | `due` | yellow | due for re-verification soon |
| > 90 days | `stale` | red | breached the SLA |

The mapping is `freshnessStatus(age)` in `rules.mjs`. Its consumers — the repo-wide badge (§3), the worklist (§4) and, since the shared-rows refactor, the `VERIFIED` column in the explorer table (§6), with the trust line (§7) reading the same numbers — all draw from this one function (or its serialised copy), so they cannot disagree about an entry's state.

## 3. The badge (`badge-freshness.json`)

The shields.io freshness badge is generated by `scripts/build.mjs` via `freshnessBadge(providers, today)` in `rules.mjs`.

**It is graded on the oldest verified entry, not on the share of entries inside the SLA.** The share was unusable as a signal: because the list is re-verified in sweeps, a share-based badge could not leave brightgreen until roughly a third of the dataset had gone overdue — about four months of complete silence. It measured whether the project was still alive, not whether the data was fresh. The worst entry moves the day maintenance stops, and it is also the number a reader actually needs: the staleness of the row they are about to trust. (Full discussion in [methodology.md](methodology.md).)

| Oldest verified entry | Badge colour |
|---|---|
| ≤ 60 days | `brightgreen` |
| 61–90 days | `yellow` |
| > 90 days | `red` |
| nothing verified | `red` |

**One override:** if fewer than 70% of rows are verified at all, a brightgreen badge drops to yellow, however recent those verifications are. Coverage still counts.

**Date-relative by design.** The badge must move when time passes, not only when the data changes — a freshness badge that only moves when the data moves is not measuring freshness. So `badge-freshness.json` is the one committed, generated file that moves with the *current date* (independent of the data), and it is deliberately **excluded** from both drift gates (`npm run check` and the CI drift report). It goes stale between refreshes on purpose and is recommitted on every data/build pass. Nothing may assert that the committed badge equals a freshly built one — on any day but the last refresh it does not.

## 4. The worklist (`npm run worklist`)

[`scripts/staleness.mjs`](../scripts/staleness.mjs) prints a Markdown re-verification checklist from the data. Report-only — it never edits anything and never fails. Sections:

- **🔴 Overdue** (`> 90` days) — every entry that breached the SLA, oldest first.
- **🟡 Due soon** (`61–90` days) — entries that will breach it next, oldest first.
- **⚠️ Never independently verified** — `verified: false` entries, with the first sentence of their `notes` as context.
- **📅 This week's batch** — the pacing target, sized as described below.
- **⛰️ Cliff watch** — only when relevant, described below.

**Cliff watch.** A "cliff" is a cluster of entries that share one verification date and therefore cross the 90-day SLA together — the end-of-quarter hit that comes from sweeping the list. The script detects any date shared by ≥ 8 verified entries, and if that cluster crosses the SLA within 45 days it warns with the exact crossing date and how many days remain, so a few can be re-verified early each week to spread the load instead of taking the hit all at once.

**Batch sizing.** Steady state: all verified entries spread across the 90-day window; clearing `ceil(verifiedCount / (90/7))` of the oldest each week keeps every entry inside the SLA without a cliff. This pacing targets the 90-day SLA, not the green 60-day threshold — the badge (graded on the oldest entry) turns green only when a pass clears further than the batch. Near a cliff, the batch grows to at least `ceil(clusterSize / weeksLeft)` — whichever is larger.

## 5. The re-verification batch (`npm run reverify`)

[`scripts/reverify.mjs`](../scripts/reverify.mjs) is the agent's entry point to the system. It picks the oldest verifications (same steady-state pacing as the worklist — `ceil(verifiedCount / (90/7))`, from `SLA_DAYS` in `rules.mjs` — though only the worklist adds the cliff-aware bump on top), fetches each provider's own `docs_url`, and writes a review dossier per provider to `.freebuff/reverify/<slug>.md` (gitignored, local only):

```bash
npm run reverify                  # this week's batch (oldest first)
npm run reverify -- --batch 12    # override the batch size
npm run reverify -- --no-fetch    # offline: just print the batch
```

The script never edits `data/providers.json` — it prepares the evidence. A human or agent reads each dossier, compares the fetched docs against the dataset, and drafts the edit. Fetch failures and non-text bodies are flagged explicitly in the dossier; a JS-rendered SPA typically yields little or no extracted text, so it lands under the "(nothing extracted — review the docs manually)" marker. Either way the dossier tells you what to look at. The full ritual around it is in [update-playbook.md](update-playbook.md).

## 6. The `VERIFIED` column (SLA-aware)

Since the shared-rows refactor, the home-page table no longer shows every verified row with the same green check. The badge in the `VERIFIED` column is coloured by the same `freshnessStatus` buckets as the badge and worklist:

- **green** — fresh (≤ 60 days)
- **yellow** — due (61–90 days)
- **red** — stale (> 90 days)
- **yellow "unverified"** — never verified

Hovering shows `Verified Xd ago · YYYY-MM-DD`. The unverified case shows a yellow `unverified` badge with no date.

**Two renderers, one function.** The row markup lives in a single function, `explorerRowHtml` in [`scripts/lib/rows.mjs`](../scripts/lib/rows.mjs). `scripts/build.mjs` uses it for the server-rendered table (passing `data.generated` as the reference date, so the first paint is deterministic and the drift gate never trips on a calendar boundary), and serialises the same function to `site/shared-rows.js` (via `clientBundle()`), which the browser executes on every filter/sort repaint (passing `Date.now()`, so visitors see live freshness). Server and client cannot drift because it is literally the same function — the two-places rule from [architecture.md](architecture.md) applied to the table itself.

## 7. The trust summary line

The hero's trust line — `67/67 verified against official docs · oldest entry 15d · 90-day re-verification SLA` — is computed client-side in `site/explorer.js` from the same rules: verified count, oldest age, and `SLA_DAYS` pulled from `shared-rules.js`. It is a read-out of §2 and §3, not a separate claim.

## 8. Invariants a change must not break

- **One set of buckets.** Any code that buckets an entry by age must call `freshnessStatus` from `rules.mjs` (or consume the serialised copy) — never re-declare the thresholds.
- **A verified entry needs its date and source.** `scripts/validate.mjs` rejects `verified: true` without `last_verified` and a real `docs_url`.
- **The dataset date cannot lie.** `generated` (top of `data/providers.json`) is rejected if older than the newest `last_verified`/`added` — the validator enforces it, so sitemap, API and CITATION never expose a stale date.
- **Nothing committed may be relative to the current date.** `badge-freshness.json` is the only committed file that moves with the clock; the NEW badge and freshness colours in `site/index.html` are computed from `data.generated`, so they are deterministic per dataset snapshot. Provider pages under `site/p/` are gitignored precisely so they may use the current date; everything else committed must be byte-stable for a given dataset.
- **No freshness signal depends on a schedule.** There is no regeneration bot and no scheduled workflow at all (CodeQL runs only on PRs and pushes to main). The committed `badge-freshness.json` is recommitted on data/build passes (date-relative by design, §3) and the worklist is computed on demand; nothing regenerates either on a schedule (`verify.yml` is a per-change integrity gate, nothing more).

## Glossary

| Term | Definition | Where implemented |
|---|---|---|
| SLA | 90-day max age for a verification | `SLA_DAYS` in `rules.mjs` |
| Due soon | 60-day warning threshold | `DUE_SOON_DAYS` in `rules.mjs` |
| `fresh` / `due` / `stale` | the three age buckets | `freshnessStatus` in `rules.mjs` |
| Age | whole days since `last_verified` | `ageInDays` in `rules.mjs` |
| Badge | repo-wide shields badge, graded on the oldest entry | `freshnessBadge` in `rules.mjs` → `badge-freshness.json` |
| Worklist | per-entry re-verification checklist | `scripts/staleness.mjs` |
| Batch | this week's oldest-N re-verification targets | the same pacing formula in `staleness.mjs` and `reverify.mjs`, from `SLA_DAYS` |
| Cliff | a date-cluster crossing the SLA together | cliff-watch section of `scripts/staleness.mjs` |
| Verified column | SLA-coloured check + age tooltip per row | `explorerRowHtml` in `scripts/lib/rows.mjs` → `site/shared-rows.js` |
