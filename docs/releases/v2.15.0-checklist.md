## Rollback

Tags are never moved or deleted, and `main` is never force-pushed. A mistake that reached `main` is fixed
forward.

| What went wrong | When | Do this |
|---|---|---|
| Anything in the release pull request | Before merge | Fix on the branch, or close it and delete the branch. Nothing was published. Re-run `release:prepare` the same day from a fresh branch if needed. |
| Another pull request merged during the release | Before merge | Rebase on `origin/main`, `npm run build`, commit, re-run the drift gate (P4). |
| `Tag release` failed | After merge | Read its log. Fix the cause, then **Re-run failed jobs** on that run (the workflow has no manual trigger on purpose). Never create the tag by hand. |
| Wrong data or notes content in `2.15.0` | Tag exists, release not yet published | Do not publish. Fix forward with **2.15.1** (patch, rule 9 (a)): a normal fix pull request, then `release:prepare -- 2.15.1`. |
| Wrong text in the published notes | After publication | Edit the GitHub release text. The tag and assets stay. |
| Wrong snapshot assets | After publication | Delete the wrong assets from the release, regenerate them in a new directory (P7) and upload them again. Re-run `Mirror dataset` by hand with the tag. |
| Wrong data in a published release or a mirror | After publication | Release 2.15.1 the same day under rule 9 (a), with a line in its notes saying what 2.15.0 got wrong. Mirrors get a new version; old ones are not deleted. |
| Broken site deploy | Any time | Fix forward on `main`, or re-run the last good `Deploy site` run. |

Do **not** revert the version bump on `main`: `release:prepare` refuses a version that is not greater, and
`Tag release` would find `v2.14.2` at another commit and fail.
