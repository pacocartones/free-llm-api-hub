# Translations (i18n)

The site is written in English. A Spanish version ships in **January 2027, after v2.16**, built from the same data: there is one dataset, and the Spanish pages are generated from it by the same build. This page explains how the translation layer works, the rules a translation follows, and the plan to cover every page.

Status (December 2026): **draft scaffolding**. The home page, the provider page template and the shared header, menu and footer are translated (the vertical slice). Everything else is English, listed in [the January plan](#plan-for-january) below. A default `npm run build` writes exactly what it wrote before this layer existed.

## How it works

| Piece | Where | What it does |
|---|---|---|
| Catalogues | `i18n/en.json`, `i18n/es.json` | One flat key per string (`nav.models`, `provider.limits`). English is the source. |
| Helpers | `scripts/lib/i18n.mjs` | `createI18n(locale)` returns `t`, `text`, `date`, `time`, `number`, `shortMonth`, `month`; also the hreflang and sitemap helpers. |
| Translated pages | `scripts/lib/i18n-pages.mjs` | The Spanish home body and provider page body, as pure functions (data in, HTML out). |
| Shell | `scripts/build.mjs` (`siteHeader`, `primaryNav`, `siteFooter`, `htmlPageRaw`) | Every word comes from the catalogue; `htmlPage({ i18n, home, alternates, langSwitch })` picks the locale. |
| Tests | `scripts/i18n.test.mjs`, `scripts/i18n-build.test.mjs` | Catalogue parity and rules; English byte-identical with and without the Spanish build. |

### Building the Spanish pages

```bash
npm run build:es
```

That is `node scripts/build.mjs --locales=es` (the environment variable `BUILD_LOCALES=es` does the same). It writes, on top of the English site:

- `site/es/index.html` and `site/es/p/<slug>.html` for every provider, with `<html lang="es">`, a canonical URL of their own (`https://freellmapihub.com/es/…`), and `hreflang` alternates (`en`, `es`, `x-default` → English);
- the same `hreflang` set, `og:locale` and a footer link "Español" on the English twins (the home page and each `/p/<slug>`), so the alternates are reciprocal;
- `site/es/sitemap.xml`, every Spanish URL with its `xhtml:link` alternates, listed in `site/sitemap-index.xml`.

`site/es/` is gitignored and left out of `derived-fingerprints.json` while it is a draft. A plain `npm run build` removes `site/es/` and the alternates again, so **do not commit the output of `npm run build:es`**: run `npm run build` before committing (it restores `site/index.html`, `site/sitemap-index.xml` and the provider pages byte for byte; `scripts/i18n-build.test.mjs` checks this).

### Byte-identical English

Without `--locales`, every English file is byte-identical to the build before i18n: the shell reads the same words from `i18n/en.json` through the same escaper (`escapeAttr`), and every locale-only addition (hreflang, `og:locale`, the language link) is written only when another locale is built. Two checks hold this:

- `npm run check` (the drift gate): the committed pages and `derived-fingerprints.json` must not move. This change passes it without regenerating a file.
- `scripts/i18n-build.test.mjs`: builds without, with, then again without `--locales=es` in a private copy of the tree. A default build writes no `site/es/` and no `hreflang`; with Spanish, only the home page, the provider pages and the sitemap index change, and only by the lines listed above; the third build is byte-identical to the first.

## Adding or changing a string

1. Add the key to `i18n/en.json` (the source). Name it `<area>.<what>`: `shell.*`, `nav.*`, `footer.*`, `common.*`, `home.*`, `provider.*`, `limit.*`. A key ending in `_html` holds trusted markup written in the catalogue (`<strong>`, a link with `{url}`); every other value is plain text and `t()` escapes it.
2. Add the same key to `i18n/es.json` with the translation. Keep every `{placeholder}` of the English value; the test fails otherwise.
3. Use it: `L.t('provider.limits')` for HTML, `L.text('provider.title', { name })` for plain text (titles, meta descriptions), `L.tHtml(key, params, ['date'])` when a param is already HTML (a `<time>` from `L.time()`, a link).
4. Plurals: write the value as an object of `Intl.PluralRules` categories and pass `count`:

   ```json
   "home.recheck_days": { "one": "Revisado en el último día", "other": "Revisado en los últimos {count} días" }
   ```

   `L.t('home.recheck_days', { count: 7 })` → "Revisado en los últimos 7 días". `{count}` is printed with the locale's digits.
5. Run `npm test`. `scripts/i18n.test.mjs` checks that both catalogues have the same keys, the same placeholders and the same plural shape, and that only `_html` keys carry markup. A key missing from `es.json` falls back to English and `npm run build:es` lists it.

Params are always escaped: a provider name from the data can never inject markup. Never build a sentence by concatenating translated fragments; give the whole sentence one key with placeholders, since word order differs between languages.

### Dates and numbers

- Dates: `L.date('2026-11-24')` → "24 nov 2026" in Spanish (short months as the RAE abbreviates them, lower case, no stop: ene, feb, mar, abr, may, jun, jul, ago, sept, oct, nov, dic); English keeps `humanDate` ("24 Nov 2026"). `L.time(iso)` wraps it in `<time datetime="2026-11-24">`, so the machine-readable day never changes. Month labels: "nov 2026" (`shortMonth`), "noviembre de 2026" (`month`).
- Numbers: `L.number(14400)` → "14.400" (es) / "14,400" (en). Spanish does not group four-digit numbers: 1000.
- Machine formats never change: JSON, the API, CSV, JSON-LD, feeds and sitemaps keep ISO dates and plain numbers.

## Translation rules

1. **Quotes are never translated.** A sentence quoted from a provider's page is the evidence behind a value. It is printed verbatim, in the language it was read in, inside an element with `lang="en"` (`verbatimQuote` in `lib/i18n-pages.mjs`). Only the frame around it is translated ("De docs.example.com · leído el 24 nov 2026").
2. **Dataset text is shown as recorded.** The free-text fields of `data/providers.json` (`free_tier`, `notes`, `rate_limits`, `best_for`, `free_limits.scope`, `commercial_ok_condition`) exist in English only, because there is one dataset. They are shown as they are, marked `lang="en"`, and the home page says so once ("El texto del conjunto de datos se muestra tal como se registró, en inglés.").
3. **Interface text, headings and data-built sentences are translated.** A sentence the build composes from fields ("Sí: Groq tiene un nivel gratuito permanente. Tarjeta de crédito: no obligatoria.") comes from the catalogue, with each value from the record.
4. **"not stated" → "no indicado".** A missing value is never "no" or "0". In Spanish it is "no indicado", used as an invariable status label ("Tarjeta de crédito: no indicado"); in a full sentence agree it as needed ("límites no indicados").
5. **Code, model IDs, URLs, field names and product names stay as they are.** The quickstart is byte for byte the English page's; only its heading changes. "Free LLM API Hub" is the name of the site.
6. Tone: the site's voice in Spanish is plain and direct, tuteo ("Consigue una clave gratis"), European Spanish spelling. Prefer the established English term when developers use it ("tokens", "endpoints", "embeddings", "chat completions").
7. The brand tagline ("We read the docs. You ship the code.") is the owner's choice; the Spanish draft ("Leemos la documentación. Tú publicas el código.") needs Paco's sign-off before launch.
