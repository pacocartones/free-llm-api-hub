# Social Winter of Code 2027: participant guide

Welcome! This guide is for people taking part in **Social Winter of Code (SWoC) Season 7** with Free LLM API Hub. It covers how to start, how to pick and claim an issue, what a good pull request looks like here, how points and labels work, the timeline, and where to ask.

SWoC is the programme at [swoc.in](https://www.swoc.in/). It is not "Winter of Code Social" (WOCS), which is a different programme with its own rules.

This guide adds to [CONTRIBUTING.md](../CONTRIBUTING.md); it does not replace it. If the two ever disagree, CONTRIBUTING wins, and please tell us in an issue.

## Labels: one place to check

SWoC has not published the official label names for Season 7 yet. The names we use are in **one table only**: the [label table in CONTRIBUTING](../CONTRIBUTING.md#programs-social-winter-of-code-and-similar). We update that table when SWoC publishes the names.

In this guide:

- **the program label** means the program label in that table;
- **a level label** means one of the Easy, Medium or Hard labels in that table.

## How to start

1. **Register with SWoC** on [swoc.in](https://www.swoc.in/). We don't handle registration.
2. **Read this repository's basics.** Skim [CONTRIBUTING.md](../CONTRIBUTING.md), especially [Your first contribution, step by step](../CONTRIBUTING.md#your-first-contribution-step-by-step) and [Which checks to run](../CONTRIBUTING.md#which-checks-to-run). Read [AI_POLICY.md](../AI_POLICY.md) too.
3. **Set up your fork.** Fork the repository, clone your fork, and install the tools once with `npm ci`. You need the Node version in [`.nvmrc`](../.nvmrc). On Windows, see [Windows and WSL](../CONTRIBUTING.md#windows-and-wsl).
4. **Run the tests once before you change anything:** `npm test`. Then you know any later failure is yours.

## Picking and claiming an issue

- **Look for open issues with the program label and a level label.** Only those count for SWoC. Read the whole issue, its latest comments and any linked pull requests first.
- **Claim it with `/take`.** Write `/take` on its own as the first line of a comment on the issue. A bot assigns you if nobody has it. Wait for the bot's reply before you start. See [Claiming an issue](../CONTRIBUTING.md#claiming-an-issue).
- **Data issues labelled both `good first issue` and `data` are not assigned.** Don't `/take` them. Open a pull request when it is ready; the first correct, sourced pull request is merged.
- **At most two open assigned issues per person.** The bot refuses a third. Finish one, or comment `/release` to give one back. Giving an issue back is completely fine.
- **No hoarding.** Take an issue only when you are about to work on it. During the programme, an assigned issue with no activity for 7 days is released, after a ping on day 5.
- **At most two Easy merges per person.** Two merges are enough for the certificate. After that, please pick Medium or Hard issues, so newcomers still find Easy ones.
- **Everything happens in the issue, in public.** Don't ask to be assigned in a pull request or by direct message.

If you think a level is wrong, say so in the issue **before** you start. We don't change the level after the work is done.

## What a good pull request looks like here

The project's core value is trustworthy data. A good pull request:

- **Closes one issue reserved for SWoC.** Write `Closes #123` in the description (with the real issue number). Without it, the pull request does not score.
- **Does one thing.** One change, one reason. Keep to the issue's acceptance criteria.
- **Cites the provider's own page for every data change, with the date you read it.** Third-party lists, blogs and AI answers don't count as sources. If the official page doesn't answer the question, that is a useful result too: say so with the link and the date.
- **Copies quotes word for word.** Don't translate, shorten or reword them. See [docs/quotes.md](quotes.md).
- **Says how you tested it.** List the commands you ran (for example `npm test`) and their results, in the pull request template.
- **Edits the source, not generated files.** For provider data, edit `data/providers.json`; see [For provider data, edit the source](../CONTRIBUTING.md#for-provider-data-edit-the-source).
- **Is complete when you push.** See the next section for why.

### AI tools

AI help is welcome. Follow [AI_POLICY.md](../AI_POLICY.md): understand what you send, test it, check every fact at its source, and be ready to answer review questions in your own words. Telling us you used AI is optional and never counts against you. Pull requests with invented sources are closed.

### Your first pull request waits for approval

GitHub holds the checks of a first-time contributor until a maintainer approves them. Until your first pull request here is merged, **every push** waits again. During the programme we approve in batches, usually in two windows a day in January and once a day after that. So:

- Push when your change is complete, not after every small edit.
- Grey checks saying *Waiting for approval* are normal. They say nothing about your change.
- Don't close and reopen your pull request to restart checks. Push to the same branch.

After your first merge, your later pull requests run their checks straight away. More detail: [Your first PR from a fork](../CONTRIBUTING.md#your-first-pr-from-a-fork-the-checks-may-wait).

### Pull requests in review

- **Keep at most two SWoC pull requests open for review at a time.** Wait for one to be merged or closed before you open a third. This keeps the review queue fair for everyone.
- During the programme we aim to reply to a new pull request within 2 days, give a first review within 3 days and decide within 7 days. These are goals, not promises: maintainers are volunteers. Details: [Reviews and response times](../CONTRIBUTING.md#reviews-and-response-times).
- Automated review comments are advisory. A human maintainer reviews and decides every merge.

## How points and labels work

SWoC scores each merged pull request by difficulty. From [swoc.in](https://www.swoc.in/), checked 27 November 2026, verbatim:

> **Base Camp** Easy · for absolute beginners +20
>
> **The Ascent** Medium · for the steady climber +30
>
> **Summit Push** Hard · for seasoned contributors +40

And for the certificate, also verbatim from [swoc.in](https://www.swoc.in/):

> Get at least two pull requests merged into participating projects during the coding period.

How this works in our repository:

- **A maintainer adds the labels when merging.** We add the level label at merge time, copied from the issue, plus the program label. Please don't ask for labels on an open pull request.
- **Only pull requests that close an issue reserved for SWoC get labels.** That means an issue with the program label. Other pull requests are welcome and reviewed as usual, but they don't get a level label and don't score.
- **Only merged pull requests count.** A closed pull request, or one that only rewords text, reformats files or adds unsourced claims, gets no label.
- **If a merged change turns out to rest on an invented source,** we revert it and ask SWoC to withdraw its points.

SWoC runs the leaderboard and the certificates, not us. If your points look wrong, first check that your pull request is merged, closes a program issue and carries the labels; then ask SWoC.
