# Multi-account and key-rotation terms: research, November 2026

This note records, for each of the 79 providers in `data/providers.json`, whether the provider's own terms forbid
**(a)** one person holding more than one (free) account, and **(b)** rotating keys or accounts, or otherwise getting
around rate limits, quotas or usage limits. It feeds a future dataset field that API routers can read before pooling
keys or accounts. It changes no data: `data/*.json` is untouched.

Research run: 2026-11-26. Values: `yes` (an official page forbids it), `no` (an official page explicitly allows it),
`not stated` (the relevant pages were read and say nothing on the question).

## Summary

| Question | yes | no | not stated |
|---|---:|---:|---:|
| (a) multiple free accounts per person forbidden | 24 | 2 | 53 |
| (b) rotating keys/accounts or getting around limits forbidden | 45 | 1 | 33 |

- 18 providers say `yes` to both; 51 say `yes` to at least one; 26 say `not stated` to both.
- **(a) `yes` has three different shapes**, which matter for a router:
  - 14 forbid extra accounts *in order to* exceed limits or obtain more free usage (Groq, OpenRouter, Novita, Scaleway,
    Vercel AI Gateway, ElevenLabs, Sarvam AI, Rime, Tencent Hunyuan, Nutrient, Veryfi, Google Agent Platform express
    mode, MegaNova, Entrim). Nutrient's clause covers only Enterprises on the free tier.
  - 7 allow one account per person outright (Cohere, SiliconFlow (personal accounts only), ModelScope, Twelve Labs,
    Gladia, Aion Labs, PLaMo).
  - 3 limit only the free offer itself: one free plan per app and IP (NLP Cloud), no new free quota on re-registration
    (Alibaba Model Studio), the trial once per subscriber (Regolo).
- **(b) `yes` has two strengths:**
  - 15 name extra accounts or keys explicitly: the 14 purpose-bound providers above, plus SEA-LION ("Only 1 API key is
    allowed to be created per user").
  - 30 rest on a generic clause against exceeding or circumventing usage limits, rate limits or metering, which says
    nothing about accounts or keys. Rotating several free accounts to multiply a quota plausibly falls under these clauses, but the
    provider does not say so in so many words. The per-row note says which shape applies.
- **`no` is rare and weak.** OCR.space's staff say on its own forum that "more than one free OCR API key" is fine "as
  long as you do not overdo it". IBM Cloud's docs say an administrator "can create and manage multiple accounts",
  which is not specific to the free Lite plan.
- Reviewer adjustments for consistency: Hugging Face and Stability AI (b) were set to `not stated`, because their only clause is
  about bypassing safeguards or "restrictions", not usage limits (the same reading as Pinecone and Twelve Labs).
  Netlify (a) was set to `not stated`, because its "multiple or bulk accounts" wording only describes access "through
  automated means" (the same reading as Cloudflare's "scripts ... so as to produce multiple accounts").
- Gaps: no terms page could be found for Bytez (404s) or OCR.space. A few pages could be read only through a fetch service's cached copy,
  so the captured date is older than the run (oldest: 2026-05-04, Nanonets). The Speechmatics usage-policy URL returned
  404. Rows with these issues say so in their note.

## Method

- Only the provider's own pages count: terms of service, acceptable-use or usage policy, rate-limit docs, free-tier
  FAQ, and in two cases an official forum or help centre (named in the note). Third-party summaries are excluded.
- Direct HTTP was not available from the research environment, so pages were read through web extraction services
  (Parallel `web_fetch`, Firecrawl). **Date** is the UTC day the page text was captured, as the extraction
  service reported it. When the service gave no capture date, the run date (2026-11-26) is used. This is why dates differ
  between rows.
- Quotes are verbatim, in the page's language (Chinese for SiliconFlow, ModelScope and Tencent; Japanese for PLaMo).
  Some line breaks collapsed to spaces during extraction. Each quote comes from the first listed source unless the note
  says otherwise.
- `yes` for (b) requires a clause about limits, quotas, rate limits, metering or fees. A clause only about bypassing
  access controls, safety safeguards or bans is `not stated`.
- `not stated` is never `no`. As in `field_checks`, an unstated value means the pages were read and are silent; it
  does not mean the practice is allowed.
- Before the field enters the dataset, every quote should be re-read on its live page and registered with
  `npm run quotes:add` (see [docs/quotes.md](../quotes.md)). This document is research input, not verified data.

## Proposed dataset fields

Use two flags, because the questions differ: a provider can forbid several accounts but stay silent on limits (Aion
Labs), or the reverse (Cloudflare). Both follow the existing tri-state pattern (`commercial_ok`, `phone_required`):
the flag holds the answer, and `field_checks.<flag>` holds why.

```jsonc
"multi_account_forbidden": true,          // true | false | "conditional" | null
"multi_account_forbidden_condition": null, // required and non-blank when "conditional", else null/absent
"limit_circumvention_forbidden": true,    // true | false | null
"field_checks": {
  "multi_account_forbidden": {
    "status": "stated",                   // stated | source_silent | needs_account | sources_disagree
    "checked": "2026-11-20",
    "sources": ["https://console.groq.com/docs/legal/ai-policy"],
    "quote": "beyond published parameters, rate limits, or use limitations, including by registering multiple accounts or orchestrating usage between multiple organizations;",
    "note": "AUP prohibited use; the multi-account ban is tied to exceeding limits."
  },
  "limit_circumvention_forbidden": { "status": "stated", "...": "..." }
}
```

**Semantics**

| Field | Value | Meaning |
|---|---|---|
| `multi_account_forbidden` | `true` | An official page forbids one person holding more than one account, either outright or to exceed limits or get more free usage. |
| | `"conditional"` | The ban covers only part of the users or the offer, e.g. the free trial once per subscriber (Regolo), only Enterprises on the free tier (Nutrient). `multi_account_forbidden_condition` says which. |
| | `false` | An official page explicitly allows several accounts or free keys (OCR.space). |
| | `null` | Not recorded. `field_checks` says why: `source_silent`, `needs_account` or `sources_disagree`. |
| `limit_circumvention_forbidden` | `true` | An official page forbids getting around rate limits, quotas, usage limits or metering, by any means. |
| | `false` | An official page explicitly allows using several keys to raise throughput. |
| | `null` | As above. |

**Notes on the design**

- Mapping from this research: `yes` → `true`, or `"conditional"` where the clause is scoped (NLP Cloud, Alibaba Model
  Studio, Regolo, Nutrient, SiliconFlow personal accounts). `no` → `false`. `not stated` → `null` with
  `field_checks.status: "source_silent"`.
- The quote limit of 400 characters already applies to `field_checks.quote`. Every quote in the table fits, but the Tencent
  quote should be shortened to its sub-item (2) when registered.
- The schema forbids extra properties in `field_checks` entries, so the generic-versus-explicit strength of (b) goes in
  `note` for now. If routers need to tell the two apart by machine, a later schema change could add an optional
  `basis: "explicit" | "generic"` to these two entries only.
- Router guidance (for the docs, not the data): a router should not pool or rotate several free accounts or keys for one
  end user when either flag is `true` or `"conditional"`. `null` means unknown, not permission.
- The names follow the existing `*_required` / `*_ok` style and read correctly as booleans. `key_rotation_forbidden` was
  rejected: no provider's terms use the word "rotation", and the clauses cover any means of getting around limits.
